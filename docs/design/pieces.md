# Pieces: views, integrations and lenses on typed resources

Status: **target, with decisions; nothing is implemented beyond the prototype
in §1.3.** It records Michiel's long-term target for plugins (2026-10-08), the
decisions towards it, what is missing, and the work list for integrations
that come from the proxy catalog with no plugin code (§3.5, §4). It amends
[`bundles.md`](bundles.md): bundles group pieces for discovery and search, and
are not the unit of matching (D3).

Every claim is marked **checked** (with a source key, listed in
[Sources](#sources)) or **estimated**. Sources were read on 2026-10-08 at
atomic-plugins `5e7cf25`, the atomic-server pin `a12b74a` (candidate19) and
the head of ontola/atomic-server#2069, `bab52555`. Sizes are always estimated.

Michiel's statement (2026-10-08, relayed by the coordinator), verbatim:

> "On a resource with a type, or a table with a type and a row type, the following should be available: - views from the atomic-plugins catalog whose manifest announces that they match the (row) type; - integrations from the localthought.io catalog that produce the appropriate schema for the table; - Devonian lenses from the atomic-plugins catalog that can be combined with integrations from the localthought.io catalog."

## 1. The target, in short

### 1.1 The three pieces

The target, restated from the statement and §1.2; it describes no current
state, so its rows carry no marks.

| Piece           | What it is                                                                                          | Comes from                                                                                                  | Declares                                                | Needs from the host                                                                                                                        |
| --------------- | --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **View**        | A module that shows (and, with a grant, edits) a table of a row class, or one resource of a class   | The atomic-plugins catalog, [`integrations/catalog.json`](../../integrations/catalog.json)                  | In its manifest, the (row) classes it matches           | A focused offer on a matching table or resource (D3, Q-087); the drive-app iframe and `store` API; the "Allow editing" row grant           |
| **Integration** | A platform synced with a table: OpenAPI document + overlays, run by syncables, no per-provider code | The proxy's catalog (localthought.io), a dated catalog under [`overlays/catalog/`](../../overlays/catalog/) | The shared ontology class each collection produces (D4) | A **Connect** offer (Q-092), exact or through ≤ 2 two-way lenses (Q-087, Q-091); a binding per table (Q-090); a generic runner and UI (D2) |
| **Lens**        | A declarative, two-way mapping between two classes                                                  | A lens catalog next to the ontology, plus drive-local lenses that need review (Q-089)                       | Source class, target class, mapping                     | Live translation for an integration (Q-088); trust; the chain search                                                                       |

### 4.3 Our recommendation (Michiel decides)

**Estimated** throughout:

1. **Read-only catalog integrations first.** Build I1 (spec + overlays), the
   field map (O8), I3, I5, I6 and the card as the generic UI (I8), for reads
   only. Pets proves the path; Todoist, Google Tasks and Moneybird follow as
   their read quirks (K1–K6, K10) become specs and syncables support.
2. **Write-back once it is generic**: Write Preconditions (K14, K15, K17),
   the rate-limit markers (K6, K7, with P1 and P1h), a generic `held` review
   and a per-platform conflict policy. Clockify and Notion are the first
   candidates.
3. **Hand-written apps remain only until their quirks are expressed as
   extensions**, offered under the same Connect menu as Apps (#2069 already
   does this). Each is retired once its catalog form covers what its README
   promises.

## 6. Path (proposal)

**A proposal, not a decision.** atomic-plugins and Local Thought work first,
because it needs no atomic-server change. Bundles become catalog grouping
data for search (D3), which blocks none of steps 1–5 (**estimated**).

1. **ap:** the manifest field in `catalog.json` with its check, filled from
   the `renders` each app writes today (V1). The #2069 user test
   ([`split-pieces.md`](../../usertest/moderator/sessions/split-pieces.md))
   runs unchanged and informs O3 and I7.
2. **ext, then overlays:** the produced-classes spec (I1, O8), declared first
   for Pets and Todoist.
3. **ext + sync, read quirks:** K1–K6 and K10 as specs and syncables
   support; P2, P3 in the proxy.
4. **ap:** the lens catalog, version 0 (L1, after O2), and the first lenses
   (L5).
5. **The generic read-only runner and card** (I3, I6, I8), once O4 is
   decided; §4.3 step 1.
6. **as, issue drafts for Joep under the freeze:** focused offers and search
   (V2, V3, I5), host-applied lenses (L4), the binding format (I6), the review
   screen (L3), P1h, background runs (I10).
7. **Write quirks** (K7, K8, K11, K14–K18, P1), then write-back for catalog
   integrations (§4.3 step 2), then typed resources (§3.4, D1).
